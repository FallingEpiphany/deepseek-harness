# Agent Note: OAuth for MCP servers

Status: implemented

[English](2026-09-11-mcp-client-oauth.md) | 中文

## Problem

`dsh-mcp-client` 只能用在配置里写死的静态标头来认证。通过 MCP 授权流程认证的 Streamable HTTP 服务器——发现、动态注册、授权码、会轮换的刷新令牌——完全无法接入，而且这种失败没有宿主能够据以行动的形状。

MCP SDK 已经在客户端侧实现了该协议，并交给宿主一个对象 `OAuthClientProvider` 来描述其状态存放在哪里、以及如何告知用户去授权。DSH 从未提供这个对象：`createTransport` 只构造了 `new StreamableHTTPClientTransport(url, { requestInit: { headers } })`，别无其他，因此 401 以 SDK 的 `UnauthorizedError` 浮出，落进 supervisor 的通用 catch。该 catch 记录 `connection attempt failed` 并按指数退避安排重试——对于不可达的服务器这是正确反应，对于正在等待某个人的服务器则是错误反应：十次尝试之后预算耗尽，工具消失。

有两件事让这个缺口是可以补上的，而不是一块需要从零设计的平面。凭据接缝新增了第二个键空间来存放 `{ kind: 'grant' }` 记录，正是为了让「获取来的凭据」有处可放；授权接缝则描述插件如何就获取凭据与人对话。两者都还没有 MCP 消费方。

## Decision

插件拥有这条流程，凭据记录持有授权凭证，supervisor 学会一个新的区分。

**OAuth 是一个传输上的配置选择。** `oauth` 加入 Streamable HTTP 服务器的配置，省略它则逐字节保持既有的静态标头行为——两者相互独立，因此一个服务器可以同时带有两者。每个字段都由显式的 `resolveOAuthConfig` 步骤再次判定，因为程序化构造会绕过配置 schema；在那里拒绝不是合法凭据键段的 `serverName`，正是阻止两个服务器别名到同一份已存授权凭证的原因。

**SDK 驱动协议，DSH 拥有状态。** `createOAuthSession` 在 `ctx.credentials` 记录之上实现 `OAuthClientProvider`，地址为 `mcp-client/<serverName>`，因此注册信息、令牌、PKCE 校验值和发现状态是每服务器四条记录。没有凭据提供方的组合会点名拒绝加载这类服务器，而不是以未认证状态连接，因为一次授权凭证蒸发的登录会报告成功、随后每个请求都失败。已存令牌通过 SDK 自己的 `OAuthTokensSchema` 读回，因此由不兼容版本写入的文档读作「没有令牌」，而不是以畸形状态抵达传输层；令牌文档的任何字段都不会被手工搬运。

**DSH 拥有浏览器往返。** `startRedirectListener` 为且仅为一次流程绑定配置的回环端口，在使用授权码之前先把重定向的 `state` 与发起它的那次流程比对，并在每一条退出路径上释放端口：被接受的重定向、被拒绝的重定向，或流程的截止时间。期望的 state 是从已存的校验值记录读回的，而不是取自内存，因此在重启之后才到达的重定向仍会与发起它的那次流程比对。

**supervisor 点名那个人必须清除的唯一失败。** 只有 SDK 带类型的 `UnauthorizedError` 会设置「等待授权」状态，从而停止重连循环并报出 URL；其余任何失败——包括一般的 500——仍是普通中断，并按它一直使用的同一套有界计划继续重试。`ConnectionHandle.reconnect()` 是回来的路：在 supervisor 停止之后完成的授权会立即重连，而不需要重启宿主。

## Alternatives considered

**只用静态标头，并在文档里让用户去铸造长期令牌。** 成本最低且本已可用，但这正是 MCP 授权流程要取代的做法：没有轮换、没有撤销，而且凭据落在配置里——而凭据接缝存在的意义就是把它挡在配置之外。

**使用 `ctx.authorization` 流程，而不是本插件自有的监听器。** 那是请求人类介入的受认可接口，`llm-pi-ai` 是可用先例，而且它能免费让每个配置界面都有一个登录按钮。否决原因是重定向 URI 恰恰是授权服务器会精确校验的部分：动态注册的客户端必须在流程开始前就声明它将使用的 URI，因此无论由谁驱动对话，监听器都必须存在并绑定到配置的端口，而为每台服务器注册的流程背后仍然需要那个监听器。在此之上再注册流程是增量工作且仍然敞开；该接缝自身的契约——每个键一次尝试、通过 `ctx.credentials` 确认一次提交——已经由记录的写入方式满足。

**令牌放进 settings 命名空间。** settings 在会被同步与渲染的明文文档中存放字面值；凭据存储才是为密钥准备的那一半，而 `llm-pi-ai` 已经确立了授权凭证属于那里。

**复用抛出异常的那个 transport，在它上面调用 `finishAuth`。** SDK 在 transport 上暴露 `finishAuth`，这暗示要把失败的实例保活到用户返回。SDK 自带的完整示例做的正相反——它用新的 transport 重试——而模块级 `auth()` 直接接受授权码，因此回调完成换取并存储令牌时完全不需要引用抛出异常的那一代。这消除了一整类生命周期问题：没有任何东西需要活过那次失败的尝试。

**把 401 当作普通中断处理。** 这不需要新的 supervisor 状态，而它恰恰是重试预算无法修复的失败。预算的存在是为了熬过一个宕掉的服务器，而不是为了等一个人。

## Consequences

伴随插件通过宿主的 `mcpConnections` 目录读取资源和提示，不复制令牌或自建传输。目录遵循工具注册的 Agent 作用域，连接卸载后移除注册。每次读取使用当前受管理的连接代次，由宿主统一负责 OAuth 刷新和重连。OAuth 组合必须声明凭证服务的配置行依赖；持久凭证服务负责跨宿主重启保留授权。

严格启动会保留等待浏览器授权的插件及其回调监听器。等待状态必须同时有已发起的授权请求和 SDK 的明确未授权结果；其他故障仍按配置使启动失败。插件入口测试联合验证 SDK 发现、回调换取和 supervisor 重连。传输故障会输出底层错误码但不输出底层请求详情，使网络诊断不必仅凭 `fetch failed` 猜测原因。

通过 MCP 授权流程认证的服务器现在是可达的，其授权凭证存放在所有其他获取来的凭据所在之处：轮换它在下一个请求即生效，而一台服务器的记录从另一台的记录无法抵达。

代价是一个固定端口和一个人。授权码流程无法在缺少可达重定向 URI 与无人完成浏览器步骤的情况下完成，因此没有预注册客户端的无头部署无法使用这条路径——SDK 的非交互提供方是那种场景的答案，目前尚未接线。这两条事实都记录在包的已知限制中，而不是留给用户去发现。

插件现在依赖凭据接缝。它通过 `ctx.get` 读取，因此没有存储的组合只会拒绝 OAuth 服务器，而不会加载失败；静态标头路径在完全没有凭据提供方时照常工作。

每台 OAuth 服务器会在 `mcp-client/` 下累积四条记录：授权凭证、注册信息、校验值和发现缓存。目前还没有任何东西为用户枚举它们，卸载插件也会把它们留在原处——凭据接缝会把这种记录报告为孤儿，并把识别工作交给调用方做的一次 join，而这里没有任何调用方做这件事。
